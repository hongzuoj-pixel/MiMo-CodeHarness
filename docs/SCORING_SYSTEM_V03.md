# MiMo-CodeHarness Scoring System v0.3

## Why v0.3 exists

Earlier scoring versions mostly evaluated whether an answer *looked complete*. That is useful for a demo, but it is not enough for a paper-style evaluation system. Two different repositories may receive the same score if the model writes similarly structured answers.

v0.3 changes the philosophy:

> A score is only meaningful when we also report the evidence behind it.

Therefore, every run now reports component scores and an `evidence_level`.

## Components

| Component | Meaning |
|---|---|
| `repo_grounding_score` | Whether the answer cites real related files, paths, modules, functions, or code references. |
| `task_rubric_score` | Whether it covers task-specific scoring points and optional human rubric items. |
| `answer_completeness_score` | Whether the answer is structured, sufficiently detailed, and actionable. |
| `patch_verification_score` | Whether patch-required tasks provide verified/applicable patches. |
| `build_test_score` | Whether safe checks or real build/test checks pass. |
| `llm_judge_score` | Optional external judge score loaded from JSON/CSV or generated by a judge model. |
| `human_review_score` | Optional human review score for calibration. |

## Evidence levels

| Level | Meaning |
|---|---|
| A | Has LLM judge + human review + patch evidence + passing build/test. |
| B | Has LLM judge or human review, and build/test evidence is acceptable. |
| C | Automatic scoring plus build/test evidence only. Useful for engineering tracking, not final paper claims. |
| D | Weak or failing evidence; manual review required. |

## Honest reporting rule

Do not report only `final_score`. Report it as:

```text
final_score = 82.4, evidence_level = C, missing_evidence = llm_judge;human_review
```

For teacher/research communication, say:

> The harness supports automatic scoring and evidence logging. Current results are automatic scores unless LLM judge/human review columns are filled.

## Recommended final-paper protocol

1. Run automatic scoring on all cases.
2. Randomly sample 20%-30% tasks for human review.
3. Run LLM judge on all or sampled tasks.
4. Compare automatic score vs. human score and report disagreement.
5. Use `build/test` and `patch` evidence as hard constraints when applicable.

This prevents the project from pretending that heuristic scoring is a perfect truth.
